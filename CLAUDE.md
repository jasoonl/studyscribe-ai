# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

StudyScribe AI is a full-stack app: a React SPA + Express/tRPC API for recording, uploading, or importing-by-link lectures/meetings, transcribing them (AssemblyAI, with speaker diarization), and generating AI study tools (flashcards, study guides, quizzes, email drafts, an AI tutor chat) from the transcript. Auth is custom (invite-gated email/password + Google OAuth), backed by a TiDB Cloud (MySQL-compatible) database via Drizzle ORM.

It runs on Vercel as serverless functions today; the code also supports a standalone Node server (Railway/Render) and still contains legacy references to its original "Manus" hosting platform.

## Commands

```bash
npm install --include=dev --no-audit --no-fund   # Vercel's actual install command — use npm, not pnpm, despite packageManager: pnpm in package.json
                                                   # package-lock.json is committed so this is reproducible; keep it in sync with pnpm-lock.yaml
                                                   # (regenerate both — `pnpm install` then `npm install` — after any dependency/override change)
npm run dev        # tsx watch server/_core/dev.ts — Express + Vite middleware, picks first free port from 3000
npm run build       # vite build (client) + esbuild bundles server/_core/index.ts and standalone.ts to dist/
npm start          # runs the built standalone server (dist/standalone.js) — used by Railway/Render, not Vercel
npm run check      # tsc --noEmit
npm test           # vitest run
npm run format     # prettier --write .
npm run db:push    # drizzle-kit generate && drizzle-kit migrate
npm run db:migrate # drizzle-kit migrate (applies committed migrations in drizzle/ only)
```

Run a single test file: `npx vitest run server/authService.test.ts` (or any path). Filter by name: `npx vitest run -t "some test name"`.

A handful of server tests (e.g. `server/providerCredentials.test.ts`) call real services and fail locally without production secrets; that is expected, not a regression. The live AssemblyAI test (`server/speakerDiarization.provider.test.ts`) is skipped unless `RUN_PROVIDER_INTEGRATION_TESTS=true` and `ASSEMBLYAI_API_KEY` are set.

There is no lint script and no CI workflow in this repo (only `.github/dependabot.yml`).

## Local Development Setup

For basic local development (`npm run dev`), you need:
- `JWT_SECRET` (any string, used to sign session cookies)
- `PUBLIC_APP_URL` or `APP_URL` (typically `http://localhost:3000` or similar)
- Database connection (one of: `TIDB_HOST`/`TIDB_PORT`/`TIDB_USER`/`TIDB_PASSWORD`/`TIDB_DATABASE`, `DB_*` equivalents, or `DATABASE_URL`)

Optional but commonly needed:
- `ASSEMBLYAI_API_KEY` — if testing transcription (without it, transcription jobs fail)
- `OPENAI_API_KEY` + `OPENAI_MODEL` — if testing study-tool generation (without it, those features fail)
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` — if testing Google OAuth (email/password auth works without it)

Not needed locally: `BLOB_READ_WRITE_TOKEN`, `RESEND_API_KEY`, `VAPID_*` keys (storage, email, and push fail gracefully without them).

To work on the live recording features without keys or network, run `node scripts/dev/mock-live-services.mjs` (port 7071, no dependencies) and start the app with `ASSEMBLYAI_API_KEY=dev ASSEMBLYAI_STREAMING_HOST=http://127.0.0.1:7071 OPENAI_API_KEY=dev OPENAI_BASE_URL=http://127.0.0.1:7071/v1`. It stands in for AssemblyAI's streaming token endpoint and WebSocket (checking the token, PCM16 format and chunk sizes, answering with scripted Begin/Turn/Termination messages) and for an OpenAI-compatible chat endpoint. `MOCK_DROP_AFTER_SECONDS` exercises reconnects; `MOCK_SILENCE_IS_SPEECH=1` produces words from Chromium's fake microphone (`--use-fake-device-for-media-stream`).

For the collaboration and integration features, `node scripts/dev/mock-phase4-services.mjs` (port 7072) stands in for an OpenAI-compatible `/v1/embeddings` and `/v1/chat/completions`, a webhook receiver (`/hooks/<name>`; `/hooks/flaky` fails twice), Notion's and Google's OAuth and APIs (authorize redirects straight back), a finished AssemblyAI job and a 60-second WAV with long pauses (`/audio.wav`, for Skip silence); `GET /_log` shows what it received. Start the app with `OPENAI_API_KEY=dev OPENAI_BASE_URL=http://127.0.0.1:7072/v1 OPENAI_EMBEDDING_MODEL=mock-embed NOTION_CLIENT_ID=dev NOTION_CLIENT_SECRET=dev GOOGLE_CLIENT_ID=dev GOOGLE_CLIENT_SECRET=dev INTEGRATIONS_TEST_BASE_URL=http://127.0.0.1:7072 WEBHOOKS_ALLOW_PRIVATE_TARGETS=true`, plus `NODE_OPTIONS="--import ./scripts/dev/redirect-assemblyai.mjs" ASSEMBLYAI_API_KEY=dev` to let a recording seeded as `processing` (provider id `mock-…`) complete through the polling path. `INTEGRATIONS_TEST_BASE_URL` and `WEBHOOKS_ALLOW_PRIVATE_TARGETS` are ignored when `NODE_ENV=production`.

## Architecture

### Server bootstrapping — one Express app, three entry points

`server/_core/app.ts` builds the single Express app (`createApp()`) shared by every runtime target. Three separate entry points wrap it:
- `server/_core/index.ts` — the Vercel serverless handler (`api/index.mjs` imports the built `dist/index.js` and re-exports it as the default handler). It also starts a real listener if run directly (`isDirectNodeExecution`), which is how the standalone path works.
- `server/_core/standalone.ts` — explicit standalone entry for Railway/Render (`npm start`).
- `server/_core/dev.ts` — dev server: wires in Vite's middleware (`setupVite`) for HMR, and calls `resumeProcessingRecordings()` on boot to pick back up any transcriptions that were mid-flight.

Because `app.ts` must stay importable by the Vercel function without pulling in Vite/static-serving code, don't add Vite-only imports there — put dev-only wiring in `dev.ts`.

### Routing inside the Express app

- REST routes for auth (`server/authRoutes.ts`), Google OAuth (`server/googleOAuthHandler.ts` + `server/_core/oauth.ts`), the AssemblyAI webhook (`server/transcriptionWebhook.ts`), storage proxying (`server/_core/storageProxy.ts`, registered via `registerStorageProxy`), and a gated one-time schema-init endpoint (`server/schemaInit.ts`). Auth endpoints are rate-limited (`server/_core/rateLimit.ts`, `express-rate-limit`), which depends on `app.set("trust proxy", 1)` in `server/_core/app.ts` so limits key on the real client IP behind Vercel's proxy; the tRPC `requestInvite` mutation uses `checkTrpcRateLimit` for the same reason.
- Everything else goes through tRPC at `/api/trpc`, defined in `server/routers.ts` (`appRouter`), which composes `systemRouter`, `customAuthRouter`, `notificationsRouter`, and the main routers for recordings/transcripts/study notes/flashcards/quizzes/study guides/email drafts/chat/browser push.
- tRPC procedure tiers (`server/_core/trpc.ts`): `publicProcedure`, `protectedProcedure` (requires `ctx.user`), `adminProcedure` (requires `role === 'admin'`). Auth state comes from a signed session cookie, resolved once per request in `server/_core/context.ts` (`createContext`) — there is no Manus OAuth fallback anymore, only the custom cookie session.

### Working with tRPC

All procedures are defined in `server/routers.ts` and composed into `appRouter`. A typical procedure:
- Inherits from `publicProcedure`, `protectedProcedure`, or `adminProcedure`
- Calls input schema via `.input(z.object(...))` (Zod)
- Uses `.mutation()` or `.query()` with a handler receiving `{ input, ctx }`
- `ctx.user` is available in `protected`/`admin` tiers; initial auth check happens in `server/_core/context.ts`

Example: `recordings.getStatus` is a query that polls transcription progress; the polling fallback calls `advancePollingTranscription` internally. If adding webhook-driven completion for a new async service, follow the same pattern: submit returns immediately, a webhook or periodic poll drives completion.

### Auth model

Invite-gated signup: `/api/auth/signup` requires a valid, unused, unexpired invite code tied to the signing-up email (`server/authService.ts`). Login supports email/password (bcrypt) and Google OAuth (`server/googleOAuthHandler.ts`); `loginWithGoogleExistingOnly` intentionally rejects unknown Google accounts on the login page (no silent account creation) while the signup path auto-creates. `getSafeApplicationOrigin` (`server/email.ts`) allowlists which origins the Google OAuth redirect/state and password-reset links may point to — extend `knownVercelOrigins`/`knownManusOrigins` there if the app moves to a new domain, since anything not on the allowlist silently falls back to the configured default origin.

Admin-invite-approval UI exists (`client/src/pages/AdminInviteRequests.tsx`, `AdminInviteCodes.tsx`) for admins to review `/request-access` submissions and issue codes, gated by `adminProcedure`.

### Database — TiDB Cloud via Drizzle, multiple env-var shapes

`server/db.ts` is the single source of truth for the DB connection and every query helper (no repository classes — just exported functions per entity, e.g. `getUserByEmail`, `createRecording`). `getExternalDatabaseConfig()` resolves the connection in this precedence order, because TiDB Cloud's "Connect" dialog and Vercel's own conventions have both been used historically:
1. `TIDB_HOST`/`TIDB_PORT`/`TIDB_USER` (or `TIDB_USERNAME`)/`TIDB_PASSWORD`/`TIDB_DATABASE` (or `TIDB_DB_NAME`) if *all* are present.
2. Same shape with a `DB_` prefix instead of `TIDB_`.
3. Otherwise falls back to `DATABASE_URL`.

An incomplete `TIDB_*`/`DB_*` set must not shadow a working `DATABASE_URL` — that's a real regression that happened once already (see git history around `getExternalDatabaseConfig`). `normalizeTiDbDatabaseName` redirects TiDB's protected default schemas (`sys`, `mysql`, etc.) to `test`. `drizzle.config.ts` re-implements the same precedence independently for CLI commands (`db:push`/`db:migrate`) — keep both in sync if the resolution logic changes.

Schema lives in `drizzle/schema.ts` (users, recordings, transcripts, studyNotes, flashcards, flashcardReviews, chatHistory, tags + join tables, userNotifications, pushSubscriptions, inviteCodes, inviteRequests, passwordResetTokens, studyGuides, quizzes, quizAttempts, emailDrafts, recordingShares, appSettings, recordingBookmarks, courses, recordingCourses, actionItems, vocabularyLists, examPacks, followUpSuggestions). Migrations are committed SQL files under `drizzle/*.sql`, generated offline with `DATABASE_URL=mysql://u:p@127.0.0.1/x npx drizzle-kit generate --name <name>` (generate never connects; the config just requires a URL). Deploys do not apply them: the one-time schema-init endpoint has already run, so every new migration needs `npm run db:migrate` against production by hand. Code that depends on a new table should keep working until then, the way `server/bookmarks.ts` treats a missing `recordingBookmarks` table as "no bookmarks"; TiDB does not support every MySQL default expression (e.g. `DEFAULT (now())` and JSON column defaults have both caused migration failures before — use `DEFAULT CURRENT_TIMESTAMP` and no JSON defaults).

### Provider abstractions (swap points if changing services)

- **Storage**: `server/storage.ts` — Vercel Blob (`isVercelBlobStorageConfigured`) is primary; falls back to legacy "Forge" (Manus's built-in storage API, `BUILT_IN_FORGE_API_URL`/`_KEY`) if Blob isn't configured. Browser uploads go directly to Blob via presigned tokens (`createDirectAudioUpload`, `client/src/lib/directAudioUpload.ts`); files over 50MB are sent in parts with the SDK's `uploadPresigned` (multipart) through `/api/storage/upload-presigned` (`issueLargeUploadToken`), because a single PUT of several hundred MB is rejected with "Failed to fetch". Browsers report a blank or generic type for some files (notably `.mov`), so the client and `createDirectAudioUpload` fall back to the file extension (`EXTENSION_CONTENT_TYPES`); QuickTime/MP4 video is stored and transcribed as `audio/mp4`; the per-recording caps (1GB upload, 500MB link import) live in `shared/const.ts` so the UI text and server checks share one value. The binding limit is the Blob store's total size: the project is on Vercel's Hobby plan (1GB), and a store over its limit is suspended so every upload fails. The Admin page shows usage (`diagnostics.storage`, `BLOB_STORAGE_LIMIT_BYTES` overrides the 1GB default once the plan changes). Soft-deleting a recording (Trash) keeps its audio; only `recordings.permanentDelete`/`emptyTrash` remove it (`purgeRecordings` deletes the audio first and aborts if that fails, so a file is never orphaned).
- **Transcription/diarization**: `server/speakerDiarization.ts` — AssemblyAI. Submission (`submitTranscriptionJob`) and status (`checkTranscriptionStatus`) are separate calls, and **no request may wait out a whole transcription**: Vercel functions have a 60s `maxDuration` and don't guarantee unawaited work runs after the response is sent, so a long in-request poll silently strands the recording in "processing" (this happened). Completion is instead driven one of two ways, chosen by `isAssemblyAiWebhookConfigured()` (needs `ASSEMBLYAI_WEBHOOK_SECRET` + `PUBLIC_APP_URL`, not just the API key):
  - **Webhook mode**: AssemblyAI calls back `server/transcriptionWebhook.ts`.
  - **Polling mode** (the fallback when the webhook isn't configured): the client polls `recordings.getStatus` every 3s while a recording is `processing`, and each call runs one `advancePollingTranscription` check. Every page that shows a processing recording (`Record`, `Upload`, `RecordOrUpload`, `RecordingDetail`) must keep polling, or that recording never resolves in polling mode. `finalizeCompletedTranscription`/`finalizeFailedTranscription` in `server/routers.ts` are the single completion path for both modes.
  - A job that finishes with no text (silence, music, unintelligible audio) resolves as a failure, `NO_SPEECH_ERROR`, in both modes; the provider's own "no spoken audio" language-detection error is mapped to the same message. Never let a `completed` provider status with empty text fall through to "processing" — that spins the recording forever.
  - `normalizeDiarizedSegments` splits long single-speaker turns at sentence ends and at gaps of 6s+ between words, because the provider returns one utterance per speaker turn and a lecture would otherwise be one unseekable block.
  - Language: by default the provider detects the spoken language (`language_detection`). `create`, `createFromUrl` and `retryTranscription` accept an optional `language` (codes in `shared/languages.ts`, picked with `LanguageSelect`), which is sent as `language_code` instead. The provider has no Cantonese; it comes out as Chinese (`zh`). Add a code to `shared/languages.ts` only if the provider lists it.
  - The admin-only `diagnostics.transcription` procedure (shown on the Admin page) reports which mode and which env vars are active. Check it first when transcripts fail: a missing `ASSEMBLYAI_API_KEY` otherwise looks like a generic failure.

  Three more pieces of this pipeline exist for non-obvious reasons and shouldn't be simplified away:
  - `server/transcriptionAudioLink.ts` issues HMAC-signed, 24h links for the provider to fetch audio from *this* server. Stored objects deliberately use a neutral `.bin` key and generic content type to satisfy storage's content-type policy, so the provider would otherwise get no format hint; storage's own signed URLs also expire before a queued job downloads.
  - `server/urlAudioImport.ts` fetches user-supplied links, so it is an SSRF surface: every hostname is DNS-resolved and rejected if it lands in private/loopback/link-local space, and redirects are followed manually (max 3) so each hop is re-checked. YouTube links are handled by `server/youtubeAudio.ts` before any of this: it asks YouTube's player endpoint (iOS client, Android VR fallback) for the audio streams, picks one (`pickAudioFormat`), requires the download host to be `googlevideo.com`, and streams it in ranged chunks. It is an unofficial endpoint, so YouTube may change it, and it challenges datacenter IPs (Vercel included) with a bot check on every client, so on Vercel it only works when `YOUTUBE_PROXY_URL` points at a residential proxy (sticky session: the stream URL is bound to the requesting IP, so the audio download uses the same proxy). The free alternative is the self-hosted relay (`scripts/youtube-relay/relay.mjs`, `npm run relay`, `server/youtubeRelay.ts`): when `YOUTUBE_RELAY_SECRET` is set, every YouTube request goes through a relay on the owner's computer via a Cloudflare quick tunnel. Requests and responses are HMAC-signed (timestamp + nonce), the relay only fetches the player endpoint and `*.googlevideo.com/videoplayback` with DNS pinned to public IPs, and the tunnel address it registers (`/api/youtube-relay/register`, stored in `appSettings`) must never be returned to clients. The Admin page's "YouTube import" card (`diagnostics.youtube`) shows what each client gets from the deployed server. Every failure maps to an explanatory error (`describePlayabilityFailure`). Other streaming-page hosts whose terms forbid media extraction (Vimeo, SoundCloud etc., `STREAMING_PAGE_HOSTS`) are refused with an explanatory error rather than scraped. Direct media links work, and so do ordinary web pages that publish a media file: `server/mediaPageResolver.ts` pulls candidates from Open Graph tags, `<audio>/<video>/<source>`, JSON-LD and download links, then each candidate is fetched through the same SSRF checks (one level deep only). An HTML response is never treated as audio even if the URL ends in `.mp3`, and servers' alternate content types (Wikimedia's `application/ogg`, `audio/x-mp3`, …) are normalised through `CONTENT_TYPE_ALIASES` before storage, which only accepts the canonical ones. `recordings.createFromUrl` tees the fetched stream into Blob storage and the duration probe in a single pass.
  - The webhook answers an **unknown transcript id with 503, not 204** — the provider id is written only after submission returns, so a short clip can call back first; a 204 would tell the provider delivery succeeded and permanently lose the transcript. Failed recordings recover via `recordings.retryTranscription` rather than re-upload.
- **Audio playback**: `server/_core/storageProxy.ts` serves recording audio with HTTP byte-range support — required or Safari won't play or seek at all. It also falls back to slicing the full body (206/416) if the storage backend ignores `Range`.
- **Recording duration**: `MediaRecorder` output (WebM/MP4) carries no duration header, so `<audio>.duration` can be `Infinity`/NaN, and Safari never resolves it on its own. Duration is therefore measured explicitly: `client/src/lib/probeAudioDuration.ts` for uploads/recordings, `server/audioDuration.ts` (`music-metadata`) for link imports, and `AudioPlayer` resolves streamed-length audio itself. `duration` of `0` means "unknown" and `formatRecordingDuration` (`client/src/lib/formatDuration.ts`) renders it as "Unknown" — always use that helper rather than formatting minutes inline.
- **Microphone recording**: one recorder for the whole app, `RecorderProvider` (`client/src/contexts/RecorderContext.tsx`), mounted above the router; `Record` and `RecordOrUpload` only render its state. A recording must run until the user presses Stop, whatever else they do, so don't move recording state back into a page (it would end when the page unmounts). Elapsed time comes from timestamps (`client/src/lib/recordingClock.ts`), not a ticking counter, because Chrome throttles timers in background tabs and the count is saved as the recording's duration. Audio is flushed every second and mirrored to IndexedDB (`client/src/lib/recordingBackup.ts`); the record pages call `restoreUnsaved` to offer it back after a crash or reload, skipping sessions still live in another tab (Web Locks) or owned by another user. The mic feeds the recorder through a Web Audio node so a disconnected device can be replaced without restarting the recorder. Skip silence in `AudioPlayer` (opt-in, `studyscribe_skip_silence`) jumps over gaps of 2s or more between transcript segments (`shared/silence.ts`); it needs the segments passed in and does no audio analysis. `RecordingIndicator` shows a floating pill whenever no page shows the recorder (`useShowsRecorder`). "Mark moment" (button or the B key, ignored while typing) stores seconds in the recorder and its backup; they are sent with `recordings.create` and shown under the player by `RecordingBookmarks`. Every source feeds one mix `GainNode` that the MediaRecorder records: the mic, and tab or screen audio (A3, `addTabAudio`/`start({ tabAudio })`, `getDisplayMedia` with `video: true` because Chrome requires it, the video track stopped at once). Tab audio is offered only on desktop Chromium (`canCaptureTabAudio`); the share is requested before the mic so the click still counts as a user gesture, and when the user stops sharing only that source leaves the mix. The mix is exposed as `audioTap` for live transcription; never open a second mic stream for it.
- **Live transcription while recording** (A1): `LiveTranscriptProvider` (`client/src/contexts/LiveTranscriptContext.tsx`), mounted inside `RecorderProvider`, follows the recorder. An AudioWorklet (`client/src/lib/liveAudioWorklet.ts`, loaded via `?worker&url`, no outputs so nothing reaches the recording) downsamples `audioTap` to 16 kHz PCM16 in 100 ms chunks (`client/src/lib/pcm.ts`), and `LiveTranscriber` (`client/src/lib/liveTranscription.ts`) streams them from the browser to AssemblyAI's Universal-Streaming v3 socket (`wss://streaming.assemblyai.com/v3/ws?sample_rate=16000&encoding=pcm_s16le&speech_model=…&format_turns=true&token=…`). The token comes from `recordings.liveToken`, which calls `GET /v3/token?expires_in_seconds=60&max_session_duration_seconds=3600` with the API key (`server/liveTranscription.ts`); the key never reaches the browser and no function holds a socket. Streaming is billed per second the socket is open, so live text is opt-in per browser (`studyscribe_live_transcript`, off by default), pausing the recording terminates the session, and `LIVE_TRANSCRIPTION=off` turns it off server-wide. The transcriber queues audio until `Begin`, rolls over to a fresh session 90s before the hourly cap without a gap, reconnects with backoff (giving up after six straight failures), and settles a closed session's last partial. Turns (`client/src/lib/liveTurns.ts`) are replaced while partial and final only when `end_of_turn && turn_is_formatted`, keyed by session because `turn_order` restarts. Any failure leaves the recording untouched. Live text is never stored: the record pages keep a copy after upload (`liveSnapshot`) until polling sees the batch transcript finish. `ASSEMBLYAI_STREAMING_MODEL` (default `universal-streaming-multilingual`) and `ASSEMBLYAI_STREAMING_HOST` (data residency, or the local mock; only `*.assemblyai.com` or loopback) are optional. `diagnostics.transcription.live` reports it on the Admin page.
- **Study help and captions** (A2, F6): `StudyHelpPanel` calls `ai.liveAssist` (`server/liveAssist.ts`) with the last 2 to 5 minutes of live text (`liveWindowText`, capped at 6,000 characters) for explain / recap / likely exam points / questions to ask / a custom question; 450 tokens, a 25s `timeoutMs` on `invokeLLM`, and 20 calls per 5 minutes per user. It is labelled "Study help", always visible, and the consent notice stays on the record pages: no hide-from-screen-share or stealth mode (roadmap section 7). `LiveCaptions` is a full-screen white-on-black view (Radix Dialog for focus trap and Esc) with five text sizes (+/- keys, `studyscribe_caption_size`).
- **Transcript tools** (`client/src/components/TranscriptView.tsx`): search with match navigation, follow-along scrolling that pauses for 5s after the user scrolls, comments and highlights on a text selection (`TranscriptAnnotations.tsx`; each line also has a keyboard-reachable comment button), and TXT/SRT/VTT export (`client/src/lib/transcriptExports.ts`). Editing a transcript changes `fullText` only, not `segments`, so the TXT export falls back to `fullText` when the two differ. Speaker names live only in `segments[].speaker`; `transcription.renameSpeaker` rewrites them, and renaming to an existing name merges two speakers. LLM prompts use `fullText`, which has no speaker names.
- **Courses and tags** (`server/courses.ts`, `server/tagsRouter.ts`, `server/organizationInput.ts`, migration 0019): a recording belongs to at most one course through the `recordingCourses` join table, not a `recordings.courseId` column, on purpose: Drizzle selects every column in the schema, so a column that production has not migrated yet would break every recordings query, while a missing table only turns courses off (`courses.ts` tolerates `ER_NO_SUCH_TABLE` like `bookmarks.ts`). `recordings.list` and `recordings.get` return `courseId` and `tagIds` (`attachOrganization`) and `list` takes an optional `courseId`. Colours are keys from `shared/courseColors.ts` mapped to `--course-*` tokens in `client/src/index.css`; legacy hex tag colours fall back to blue. There is no sidebar: the dashboard (not `DashboardLayout`, which is an unused template) shows a `CourseStrip` above the library, `/courses/:id` (`CoursePage`) reuses `RecordingList`, and `RecordingOrganizer` (folder button on rows, "Filed under" on the recording page) sets course and tags. Purge, account export and account deletion cover courses, assignments and recording tags. Archiving a course hides it from pickers and the strip but keeps assignments.
- **Ask StudyScribe** (`/ask`, `ai.askAcrossRecordings`, `server/ask.ts`, `server/askRetrieval.ts`): keyword retrieval, no embeddings yet. Question terms (stopwords dropped, light stemming) gate a LIKE query over completed transcripts (newest 40, optionally one course), transcripts are split into ~700-char passages (from `segments` so each has a start time, or by sentence when edits made segments stale), ranked TF-IDF style with word-start matching and a per-recording cap, and the top 12 go to the LLM as numbered excerpts; the answer cites `[n]`, parsed into citations that link to `/recording/:id?t=<start>`. `RecordingDetail` reads `t` and `AudioPlayer` seeks via `startAt` once duration is known. No matching passage means no LLM call. Exchanges are stored in `chatHistory` with `recordingId` null (nullable since migration 0019; the insert is skipped with a warning before it). Rate limited to 30 questions per 10 minutes per user.
- **Phase 2 study tools** (migration 0020: `actionItems`, `vocabularyLists`, `examPacks`; every reader tolerates the tables being missing, like `bookmarks.ts`). All model calls here send a transcript condensed by `server/transcriptBudget.ts` (`condenseTranscript`: ~45s windows as `[m:ss]` lines, shortened proportionally so the whole recording stays represented, 48k chars per recording, 60k split across an exam pack by `allocateBudget`) with `max_tokens` set, and go through `server/llmJson.ts`; prompts and output validation are pure helpers (`server/studyExtraction.ts`, `server/examPackBuilder.ts`) with tests. Generation is always on request and stored.
  - **Tasks** (`server/actionItems.ts`, `actionItems.*`, `RecordingTasks` on the recording page, `/tasks`, `UpcomingTasks` on the dashboard): "Find tasks" extracts homework, readings, exams and action items with due dates resolved against the recording's date (`dueDate` is a zone-less `YYYY-MM-DD`, `dueText` keeps the words said) and the moment mentioned. Running it again replaces only open extracted items; done and hand-added ones stay. Grouping and date helpers are in `shared/actionItems.ts`.
  - **Key terms and chapters** (`server/recordingInsights.ts`, `insights.*`, `KeyTermChips` in `TranscriptView`, `RecordingChapters` under the player) are `studyNotes` rows with `metadata.insight` = `key_terms` | `chapters` and the structured data in metadata; `getStudyNotesByRecordingId` filters them out so they never show as notes or in shared views. Key terms are kept only if they occur in the transcript (each chip is a transcript search); chapters are sorted, merged when under 30s apart and start at 0.
  - **Custom vocabulary** (`server/vocabulary.ts`, `server/vocabularyInput.ts`, Settings, `VocabularyField` beside `LanguageSelect` and in the retry panel): a standing per-user list (row with `recordingId` null) plus per-recording terms given to `create`/`createFromUrl`/`retryTranscription` (`keyterms`). `startTranscription` merges them (`resolveKeyterms`, recording terms first, 200 max, 6 words each) and sends AssemblyAI `keyterms_prompt` (not the legacy `word_boost`, which newer models ignore); a 400 with terms is retried without them before the speaker-label fallback.
  - **Exam packs** (`server/examPacks.ts`, `/exam-packs`, `/exam-packs/:id`, `ExamPackDialog`, "Exam pack" on course pages): up to 12 finished recordings or a course. `create` writes the guide; the pack page then calls `generateQuiz` as a second request so neither request makes two model calls. Answers are graded server-side (`scoreQuiz`; short answers ignore case, accents, punctuation and articles). Permanently deleting any source recording deletes the pack (`deleteExamPacksForRecordings`, called from `purgeRecordings` before the recording rows go). Purge, account export and account deletion cover all three tables.
- **Study notes** (`client/src/components/StudyNotesPanel.tsx`): templates are prompt presets in `shared/noteTemplates.ts`, mapped onto the existing `studyNotes.type` enum, with the template id in `metadata`, so adding one needs no migration. Opening a finished recording without notes writes them once per tab (`client/src/lib/preferences.ts`, off switch in Settings); the notes tab is `forceMount`ed so this happens on whichever tab is open. `ai.translateNote` translates one note on request and does not store it; whole transcripts are not translated because they can exceed the 60s function limit.
- **LLM**: `server/_core/llm.ts` — OpenAI-compatible chat completion client (`OPENAI_API_KEY`/`OPENAI_BASE_URL`/`OPENAI_MODEL`), used for summaries, flashcards, quizzes, study guides, email drafts, and the AI tutor chat. Pass `timeoutMs` for calls that must finish well inside the 60s limit; it also stops the retry loop.
- **Follow-up suggestions** (C7): `followUps.*` (`server/followUps.ts`, prompt and validation in `server/followUpExtraction.ts`) stores 3 to 5 dated steps per recording in `followUpSuggestions` (migration 0021; reads return nothing and writes explain themselves until it is applied). Regenerating replaces the open ones. A daily Vercel cron (`vercel.json` `crons`, 13:00 UTC) calls `GET /api/cron/follow-up-reminders`, which needs `Authorization: Bearer $CRON_SECRET` (Vercel sends it when `CRON_SECRET` is set; without it the route answers 503) and sends one in-app notification plus browser push per person for items due that day, once each (`remindedAt`).
- **Transactional email**: `server/email.ts` — Resend (`RESEND_API_KEY`/`RESEND_FROM_EMAIL`); the sending domain must be one the owner controls and has verified in Resend (the historical default, `studyscribe-ai.manus.space`, is Manus-managed and can't be used for this).
- **Browser push**: `server/pushNotifications.ts` — Web Push with VAPID keys.
- **Embeddings (smart search)**: `server/embeddings.ts` — any OpenAI-compatible `/embeddings` endpoint, on only when `OPENAI_EMBEDDING_MODEL` is set (`OPENAI_EMBEDDING_API_KEY`/`_BASE_URL` default to the chat ones; `OPENAI_EMBEDDING_DIMENSIONS` is optional). Vectors are float32 BLOBs in `transcriptChunks`, ranked in Node by cosine over the person's own chunks (capped at 6,000, newest recordings first), not a TiDB `VECTOR` column, so the schema also runs on MySQL/MariaDB; a much larger library would want TiDB's vector index with the same table shape. Chunks are the same ~700-character passages Ask ranks by keyword (`buildPassages`), keyed by a hash of the transcript and the model, so an edited transcript or a new model is re-embedded. Indexing happens right after a transcript completes (15s timeout, failures ignored), lazily inside Ask (up to 8s for a few missing recordings) and from Ask's "Index the other" button (`smartSearch.indexNext`, bounded batches). Ask fuses keyword and embedding rankings with reciprocal rank fusion and falls back to keywords on any embedding error.
- **Outgoing webhooks**: `server/outgoingWebhooks.ts` — up to 5 endpoints per person for `recording.completed`, `transcript.ready` and `notes.generated` (`shared/webhooks.ts`). Bodies are signed `StudyScribe-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` with a per-endpoint secret stored encrypted. The URL is an SSRF surface: the host is resolved, every address must be public (`isDisallowedAddress` from `urlAudioImport.ts`), the connection is pinned to the checked address with an undici `Agent` (no rebinding between check and connect), and redirects are refused. Delivery happens on the request that caused the event with a 5s timeout; failures get `nextAttemptAt` (1 min, 10 min, 1 h, 6 h, 1 day; 6 attempts) and due retries run after the person's next event, when they open Settings, and from the existing daily cron (`/api/cron/follow-up-reminders` also calls `runWebhookMaintenance`, which prunes logs older than 30 days). Don't add a cron for it.
- **Notion / Google Docs export**: `server/integrations.ts` — per-person OAuth (`/api/integrations/{notion,google}/connect` and `/callback`, state is a signed JWT plus a nonce cookie `studyscribe_integration_state`). Notion uses a public integration (`NOTION_CLIENT_ID`/`_SECRET`); Google reuses `GOOGLE_CLIENT_ID`/`_SECRET` (or `GOOGLE_DRIVE_CLIENT_ID`/`_SECRET`) with only the `drive.file` scope, and the redirect URI `<origin>/api/integrations/google/callback` must be added to the OAuth client. Notes and guides are converted by `server/markdownExport.ts` (Notion blocks, or HTML that Drive converts to a Doc). Tokens are AES-256-GCM encrypted by `server/tokenCrypto.ts` with a key derived from `INTEGRATIONS_ENCRYPTION_KEY` (falls back to `JWT_SECRET`); changing that secret makes stored tokens and webhook secrets unreadable, so people reconnect and rotate.

### Sharing, comments and groups

Access to a recording is resolved in one place, `server/recordingAccess.ts`: owner, a direct share (`recordingShares.role`: view, comment or edit, `shared/sharing.ts`), or membership of a study group that the recording, or the course it is filed under, was shared to (`groupShares`); the strongest grant wins. Every procedure that serves shared content calls `requireRecordingAccess(recordingId, userId, neededRole)` (no access reads as NOT_FOUND so ids can't be probed): `sharing.getSharedWithMe` (view), `annotations.*` (comment; resolve is author, editor or owner; delete is author or owner), `transcription.update`/`renameSpeaker` (edit), and the storage proxy (any role). Owner-only actions (sharing, notes, quizzes, sending to apps) still check `recording.userId`. Comments and highlights (`server/annotations.ts`, `transcriptAnnotations`) anchor to a segment index/id plus character offsets and keep the quoted words; `shared/annotations.ts` validates anchors and builds threads. Editing the transcript changes `fullText` only, so anchors survive; if a line's words change, the thread shows "the transcript has changed" instead of a highlight. View-only shares and public links never see comments. Groups (`server/groups.ts`) add members by email (existing accounts only) or a join link (`/groups/join/:token`, owner can rotate or turn it off); leaving or being removed also withdraws that member's shares to the group.

Migration 0022 has to be applied by hand. Before it is, `server/schemaTolerance.ts` turns these features off: share reads fall back to selecting without `role` (every share counts as view, and a non-view role explains itself), and the new tables read as empty or "not available on this server yet". Keep new reads of `recordingShares` going through `selectShares` rather than `db.select().from(recordingShares)`, which would list the `role` column.

`purgeRecordings` also deletes comments, embeddings and group shares of the recordings; account deletion removes comments the person wrote, embeddings, the groups they own (and their memberships and shares elsewhere), webhooks and deliveries, and connected apps; account export includes all of them except secrets and vectors.

### Frontend

Vite + React 19, routed with `wouter` (not react-router) in `client/src/App.tsx`, where page components are `React.lazy` code-split — add new pages the same way. `ProtectedRoute` wraps authenticated pages and reads auth state from `useCustomAuth` (`client/src/_core/hooks/useCustomAuth.ts`), which talks to the custom REST session endpoints, not tRPC, for the initial auth check. Data fetching for everything else goes through the tRPC client + TanStack Query. Pages typically call `client.recordings.list.useQuery()` or `client.recordings.create.useMutation()` to fetch or mutate data. Mutations trigger refetches via `queryKey` invalidation (e.g., after creating a flashcard, the flashcards list query is invalidated). The tRPC client instance is wrapped in a QueryClientProvider at the app root. UI components are shadcn/ui (`client/src/components/ui`) on Tailwind v4. Path aliases (`@` → `client/src`, `@shared` → `shared/`) are defined in both `vite.config.ts` and `tsconfig.json` — keep them in sync if either changes; `vitest.config.ts` also duplicates them for tests.

The `/demo` page plays `client/public/demo/studyscribe-demo.mp4` when present and otherwise falls back to a slideshow of `client/public/demo/*.jpg` (`DemoWalkthrough.tsx`). The video (1080p, narrated with an ElevenLabs premade voice, currently "Liam"; `voice_id` lives in `v2/storyboard.json`, and library/professional voices return 402/403 on a free plan) is a motion-graphics piece built from live screenshots of the app in `scripts/demo-video/frames/` (2800x1568). To retake them: run the app against a **local** database, seed the demo library with `DATABASE_URL=mysql://…@127.0.0.1/… node scripts/demo-video/v2/seed-library.mjs` (fourteen lectures and meetings across subjects, one transcribed in Spanish, with notes, flashcards and review history, quizzes, a guide, an email draft and a tutor chat; it refuses non-local databases because it rewrites the demo user's data), then `node scripts/demo-video/v2/capture.mjs [baseUrl]`. Capture logs in as the demo user, finds recordings by title, saves every frame and writes `v2/rects.js`: each highlight and click target measured from the live page (`boundingBox`) in the 1600x896 space scenes draw screenshots in, so `scenes.js` never holds hand-measured coordinates. Some narration names seeded content ("What does AI stand for?", the 40-second reading, the 7-minute class, the 52-minute cell biology lecture, the ten-question quiz), so keep `seed-library.mjs` and `storyboard.json` in step. Callouts, highlights and clicks are timed to the narration through word timestamps from ElevenLabs. Generated narration is cached per scene in `v2/assets/narration/<id>.{mp3,json}` and only regenerated when a scene's text changes, so visuals can change freely without a key; without `ELEVENLABS_API_KEY` a changed line gets a draft system voice (macOS `say`, layout checks only). Scene visuals are timed to the narration (hook and brand text appear on the spoken words), and the look is Apple-style type and spacing on the StudyScribe blues (keep the palette). Source is `scripts/demo-video/v2/`: `storyboard.json` holds the narration and timing, `build_audio.py <workdir>` renders the voiceover, music and sound effects and writes `timeline.json` (afconvert on macOS, ffmpeg elsewhere), `index.html` + `scenes.js` define every scene as a function of time, and `render.mjs <workdir> <out.mp4>` steps through it frame by frame in headless Chrome (`npm install` inside `v2/` first; set `CHROMIUM_PATH` on Linux) and muxes the audio. Re-encode the result to `yuv420p` (`-vf scale=in_range=pc:out_range=tv,format=yuv420p`) and write it to `client/public/demo/studyscribe-demo.mp4` with `-movflags +faststart`, then refresh `client/public/demo/poster.jpg` from a frame of it. Render stills first with `--stills t1,t2` to check a change. The older Swift pipeline (`build.py`, `make-demo-video.swift`, `storyboard.json` at the folder root) is superseded.

`shared/` holds code imported by both client and server (`shared/const.ts` for shared string constants, `shared/types.ts`) — put cross-cutting constants there rather than duplicating them.

### Legal pages and consent

Policies live at `/terms`, `/privacy`, `/cookies`, `/refunds` and `/credits`, all rendered through `LegalLayout`. Operator name, contact email, minimum age (13) and the effective date come from `shared/legal.ts`; change them there, never inline. `docs/compliance/legal-checklist.md` tracks the compliance checklist and what is still the owner's to do. Analytics (Vercel Web Analytics, plus Umami when `VITE_ANALYTICS_ENDPOINT`/`VITE_ANALYTICS_WEBSITE_ID` are set) load only after the visitor accepts in `CookieBanner` (`client/src/lib/cookieConsent.ts`, localStorage `studyscribe_cookie_consent`; Global Privacy Control counts as declining), so never inject an analytics or tracking script directly; add new cookies or storage keys to the Cookie Policy table. Sign-up requires separate age and Terms confirmations, enforced server-side for email (`confirmedAge` in `/api/auth/signup`) and Google (`consented` in the OAuth state). Screenshot scripts set the consent key so the banner stays out of frames. Make click-only containers keyboard-usable with `pressable()` (`client/src/lib/pressable.ts`).

### Deployment

Vercel is the active production target: `vercel.json` builds with `npm run build`, routes `/api/*` to the bundled `api/index.mjs` handler, and serves the SPA for everything else. Deploys are automatic on push to `main` via Vercel's GitHub integration — there is no separate deploy step or CI gate to run manually; check deploy status via the GitHub commit status API (`context: "Vercel"`) or the Vercel dashboard. `render.yaml`/`railway.json`/`railway.toml`/`Procfile`/`render-build.sh` exist from an evaluated-but-not-completed migration off Vercel; don't assume they're current.
