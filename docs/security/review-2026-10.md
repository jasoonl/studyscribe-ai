# Security review, October 2026 (Phase 6)

Scope: every REST route and tRPC procedure added in Phases 1 to 5, plus the
older auth and storage paths they depend on. Areas: auth and sessions, sharing
roles, study groups, comments, API keys, outgoing webhooks, uploads and the
storage proxy, Stripe and Recall webhooks, teams and SSO, calendar and
integration OAuth, the unsubscribe flow. For each: IDOR, missing role checks,
SSRF, open redirects, CSRF on cookie-auth REST endpoints, rate limits, secrets
in responses, logs or exports, and timing-unsafe comparisons.

Method: read every `app.get/post` registration (`grep -rn "app\.\(get\|post\)" server`),
every procedure that takes a recording, note, group, team or webhook id and
how it checks ownership, every comparison of a token or secret, every place a
user row or token reaches a response or a log, and every redirect target.
Each fix below has a test; `npm test` runs them.

## Findings and fixes

## Checked and found sound

- **Ownership (IDOR).** Every procedure that takes a recording, note, flashcard, quiz, guide, draft, task, course, tag, bookmark, slide, translation or exam pack id checks `userId` against the session, or goes through `requireRecordingAccess` with the role it needs; no access reads as NOT_FOUND. Notifications filter by `userId` in the update itself.
- **Sharing roles and comments.** `annotations.*` require comment access; resolve and delete follow `canResolve`/`canDelete`; view-only shares and public links never receive comments, including the group feed (`commentable` set). The new @mentions only notify people `commentAudience` says can read the comments.
- **Groups.** Membership is checked on every group procedure; only the owner sees member emails and the join token; leaving withdraws that member's shares.
- **Teams and SSO.** `orgCan` gates every console action; SSO callback state is a signed 15-minute JWT and the profile must match the team's organisation and domain; seat limits are enforced before an account is created. The new SSO-only switch is owner-only and requires a verified domain and linked organisation.
- **API keys.** Stored as SHA-256 hashes, compared in constant time, scoped, rate limited per key; `sessionProcedure` keeps key management, billing, export and deletion session-only.
- **Webhooks (outgoing).** SSRF: hosts resolved, private ranges refused, the connection pinned to the checked address, no redirects. Secrets encrypted at rest and never exported.
- **Inbound webhooks.** Stripe and Recall verify HMAC signatures over the raw body with a 5-minute window and `timingSafeEqual`; AssemblyAI and the cron compare their secrets in constant time; the YouTube relay signs both directions.
- **Integration OAuth.** State is a signed JWT plus a nonce cookie bound to the session's user; tokens are AES-256-GCM encrypted; disconnect revokes.
- **Uploads.** Upload tokens are issued only for the session's own key prefix and size cap; `recordings.create` re-checks the key prefix and verifies the stored object.
- **Unsubscribe.** Tokens are HMAC-signed per address; GET only reads state, so mail scanners that prefetch links cannot opt anyone out.
- **Rate limits.** Auth (login, sign-up, reset), invite validation, group invites, comments, Ask, Study help, live tokens, translations, checkout, webhook tests, exports and the new smart search all have limits.

## Accepted risks and follow-ups

- ~~Sessions are still stateless JWTs: signing out clears the cookie but does not revoke a copied token.~~ Fixed in Phase 7 (migration 0033): signing out revokes the session, and Settings has "Sign out of all devices". Sessions issued before the change have no id, so a single sign-out does not revoke them, but sign out everywhere does.
- ~~Password reset tokens are stored as plain values.~~ Fixed in Phase 7: they are stored as SHA-256 hashes (no migration needed).
- Group invites by email reveal whether an address has an account to the group's owner (rate limited to 60 an hour).
- The legacy Manus OAuth route (`/api/oauth/callback`) still exists; its cookie is ignored by the session code. It can be removed once nothing links to it.
- The in-memory rate limits are per function instance on Vercel, so they bound bursts rather than enforce exact quotas.
